## 1. Quarantined content — resolved (2026-08-22): 11 rows unpublished

See `CONTAMINATION_REPORT.md` (generated by `scripts/scan_contamination.py`,
which is still read-only and doesn't reflect this decision). All 12 flagged
rows were tagged `moreno_valley_ca` but referenced Brookings/South Dakota
identity; the scanner found **zero** contamination in the reverse direction.

The report's per-row recommendations (`relocate to sister site` / `rewrite
locally` / `false positive`) turned out not to be directly actionable:
**every one of the 12 flagged slugs already has its own, independent,
legitimate row published on `brookings_sd` for the same date** (checked
directly against the live DB), and `stories` has a `UNIQUE(town_id, slug)`
constraint — so "relocate" would have collided with content already there.
"Rewrite locally" isn't a simple re-run either: `generate_article()` always
writes for *today's* date/news context, not the original historical date, so
regenerating would produce an unrelated new piece, not a corrected version of
the original.

Decision made: unpublished all 11 non-false-positive rows (`UPDATE stories
SET published_at = NULL ...`) rather than deleting — the row and text are
still in the DB for audit, they just no longer render on the live site. The
1 false positive (`home-sales-digest-2024-08`, flagged only for the word
"prairie" as a street name) was left untouched.

`culture_essay-2026-08-03` — the most heavily contaminated single piece (7
hard-blocklist terms including De Smet, Volga, Elkton; a meta-essay about a
library-listing mixup, written from Brookings' own perspective, published on
Moreno Valley) — is included in the 11 unpublished rows. Whether it warrants
a follow-up correction note (rather than just silent removal) is a separate
editorial call, not made here.

## 2. Corrections to the original audit brief

Verified independently against the live database and git history before any
code was written — worth recording here since the brief's claims aren't all
accurate as stated, and future readers of this repo shouldn't take them at
face value:

- **`culture_essay-2026-07-24` and `culture_essay-2026-07-25` do not exist**
  under any town_id. Not unreviewed — never published, full stop.
- **The "Thai characters" claim is false as stated.** Read the full raw body
  of `culture_essay-2026-08-03` directly: it's coherent English prose whose
  *subject matter* narratively describes a glitch as a literary device
  ("dissolves into a smear of stray Thai characters"). No actual non-Latin
  bytes or replacement characters in the stored text. The underlying
  encoding *vulnerability* the claim was reaching for is real (see below)
  and now mitigated — it just wasn't the cause of this specific story.
- **No rows have NULL or invalid `town_id`.** The DB write path was never
  broken; the contamination is entirely in the generated text, not the
  town_id column.
- **Timeline correction**: the brief says contamination "stops after Aug 3."
  The actual fix (`a5ebec0` + `e108341`) landed **Aug 7**, not Aug 3.
  "Clean by Aug 10" is consistent with an Aug 7 fix given roughly-daily
  rotation, but content generated Aug 3–7 needs the same scrutiny as
  earlier content, not a pass because it's "close to Aug 10." The scanner
  report already reflects this correctly (it checks actual content, not
  publish-date proximity to Aug 3) — flagging here only because the
  brief's own framing could lead a human reviewer to under-scrutinize that
  window if they trusted the "stops after Aug 3" claim at face value.
- **A sixth content type was affected but not named in the brief**:
  `kvick_essa` (`kvick_essa-2026-07-25` is in the quarantine report). It
  was fixed by the same Aug 7 commit as the five named types, just not
  called out in the original audit.

## 3. Encoding fix — worth a spot-check, not a blocking decision

`scrapers/parsers/events.py` now decodes ICS bytes explicitly (utf-8 →
cp1252 fallback, loudly logged) instead of relying on `icalendar`'s silent
`errors="replace"`, and `scrapers/text_sanity.py` flags suspicious fields
before they're stored. This is a genuine, previously-unmitigated
vulnerability (confirmed via code read of the `icalendar` package), even
though it wasn't the cause of the specific story named in the brief. Worth
watching the scrape logs for a week for any `misstänkt text` warnings to
confirm this doesn't have a false-positive rate that's a nuisance in
practice — not urgent, no content is currently known to be affected.

## 4. Phase 2 (data pipeline integrity) — items needing a human decision

Phase 2 is code-complete (site-wide timezone fix + all 6 verticals: events,
home sales, jobs, traffic, sports, weather) and covered by 38 new regression
tests (`pytest tests/` — 68 total, all green). The items below are things
the code deliberately does NOT decide on its own.

- ~~**Sept 2025 home-sales gap.**~~ **Resolved (2026-08-22): quarterly-aware
  ingestion + reconcile, not a pipeline bug.** Riverside County's Property
  Sales Report is a rolling 2-year window published quarterly, not monthly
  files — a mid-window scrape can make a real month look empty when the
  county just hasn't reached it yet, and late-recorded deeds can land in a
  *later* file than the month they belong to. Built to design around this:
  - `db/migrations/019_property_sales_ingest_metadata.sql`: explicit
    `pin`/`doc_number`/`record_date` columns (verified-unique identity, 0
    collisions across all 2610 existing rows) plus a new
    `property_sales_ingests` table recording each reconcile's countywide
    RecordDate coverage window.
  - `scripts/reconcile_property_sales.py`: upserts by `(town_id, pin,
    doc_number)` — a re-pull now heals/corrects existing rows instead of
    only adding new ones — and records the ingest window. Idempotent (ran
    twice against the same file: 0 inserted / 2610 updated / 2610 total
    both times, no dupes).
  - `ai_pipeline/home_sales_state.py`: classifies every month into
    `released_with_data` / `released_zero` / `not_yet_released` purely from
    the ingest window, never hardcoded dates — replaces the old
    `missing_trailing_months()`, which only checked *after* the latest
    month with data and so couldn't see an interior gap at all.
  - Ran the reconcile against the existing quarterly file
    (`data/property_sales/moreno_valley_ca/447569.xlsx`, still the most
    recent one on disk — see the sourcing question below) and re-ran
    `home_sales_digest.py`. **Finding: Sept 2025 is genuinely zero, not
    missing.** The file's countywide RecordDate coverage reaches
    2025-12-24, well past September, and direct inspection of the raw file
    confirms only one Moreno Valley residential row with a Sept 2025
    DocumentDate, and it has `Consideration = 0` (a non-arms-length
    transfer, correctly filtered like every other month). The site now
    shows an honest "County records show no qualifying home sales recorded
    ... for September 2025" note instead of silence. **Nov 2025 turned out
    to have the same situation** (also genuinely zero, also now flagged)
    — invisible under the old logic since Oct 2025 already had data and
    Nov was never checked as an interior month either.
  - Every month Dec 2024 → present now resolves to one of the three states
    (confirmed via direct query): 19 real digests unchanged (same
    underlying rows, no wasted AI spend), 2 `zero_sales` notices (Sept +
    Nov 2025), 9 `data_pending` notices (Dec 2025 → Aug 2026). Pending
    pages are `noindex` (`site/src/layouts/BaseLayout.astro`); they flip to
    indexable automatically the moment real data lands, since the digest
    slug gets overwritten in place.
  - **Sourcing decision needed**: this whole pass ran against the file
    already on disk (downloaded 2026-07-23) — I did not fetch a newer one.
    `rivcoacr.org/robots.txt` explicitly disallows AI agents by name
    (`anthropic-ai`, `ClaudeBot`, `Claude-Web`), so pulling a fresher
    quarterly file requires a human to download it manually into
    `data/property_sales/moreno_valley_ca/` (same as every prior pull) —
    re-running `scripts.reconcile_property_sales` afterward will
    auto-heal any month that's since been published, no code changes
    needed. Separately: confirm the free quarterly Property Sales Report
    is the right artifact to keep treating as canonical, vs. Riverside
    County's paid Bulk Data Sales product (likely shorter latency and
    finer granularity) — a sourcing/cost decision, not something to pick
    without knowing the price and how much home-sales traffic matters.
- **MaxPreps / CIF-SS accessibility — unresearched.** Every other scraped
  source in this codebase (MLB Stats API, Caltrans QuickMap, Adzuna, NWS,
  Thrillshare/Finalsite) has a documented live-verification note before any
  parser was built against it. No equivalent verification exists for
  MaxPreps or CIF-SS (real high-school sports results/schedules), and
  MaxPreps in particular is a commercial site likely behind bot protection
  (same category as the ESPN scoreboard API this codebase already declined
  to scrape, see `regional_sports_v1.py`'s docstring). Rather than guess at
  a scraper against an unverified source, Phase 2 shipped the achievable v1
  — `ai_pipeline/local_sports_weekly_digest.py`, sourced from the school
  district's own general announcement feed (`school_alerts`, already live)
  filtered to sports-relevant keywords. A human needs to research whether
  MaxPreps/CIF-SS offer any legitimate account-based or licensed feed before
  a real local-sports-results source can be built.
- ~~**Jobs backfill not yet run.**~~ **Done** — `python -m
  scripts.backfill_jobs_categories` ran against the live DB, 40 rows
  corrected. Along the way it caught a real bug in the classifier itself
  (naive substring matching turned "...Microvascular *Reconstruction*
  Fellowship" into "Construction & Trades" because `"construction"` is a
  substring of `"reconstruction"`) — fixed with word-boundary regex before
  applying for real, with a regression test pinning the exact case
  (`tests/test_jobs_parser.py::test_classify_does_not_substring_match_inside_a_longer_word`).
- ~~**16 thin Moreno Valley event stories still need deleting.**~~
  **Resolved on its own by 2026-08-22.** Re-checked before running the delete
  above: none of the 16 slugs listed still exist in `stories`, and a fresh
  scan for any `moreno_valley_ca` event row with `length(body) < 40` returns
  zero rows. Event slugs are re-derived per scrape, so a later regeneration
  already superseded these with full-content rows under new slugs — no
  manual delete was needed after all.
- ~~**home_sales_digest.py's 4 template-fallback months**~~ **Done** — added
  a `--month YYYY-MM` (repeatable) flag to scope `--force` to just the 4
  affected months instead of re-spending on all 22. Ran for real: 2024-03,
  2025-01, 2025-02 now generate real narrative prose (and correctly cite the
  new outlier-exclusion note where relevant); 2025-10 legitimately stays on
  `template_fallback` — it only has 2 recorded sales, genuinely too little
  to write 250+ words about, not a bug. As a side effect of the same run,
  10 "data pending" placeholder stories were published for Nov 2025–Aug
  2026 (the missing-trailing-months feature, `ON CONFLICT DO NOTHING`, safe).
- **Event JSON-LD has no real venue/address.** `stories` doesn't carry the
  specific venue (only the source `events` table does), so the new
  `schema.org/Event` markup in `s/[slug].astro` falls back to town-level
  location. Honest but likely insufficient for Google's full Event rich
  result — worth running through the Rich Results Test manually (no access
  to it from this environment) and considering a `stories.venue` column if
  rich results turn out to require a real address.
